# Step 4B: 検索基盤の実装計画 (Implementation Plan)

## User Review Required
> [!IMPORTANT]
> 以下の実装計画は、指示書に基づく Step 4B（検索基盤）のスコープと制約を定義したものです。
> ご確認いただき、問題がなければ承認をお願いいたします。

## 1. Step 4Aからの継続課題（技術的負債）
> [!WARNING]
> 本システム（PoC）のDB永続化基盤には以下の制限と既知の課題があり、解決済みではありません。将来のPostgreSQL等への移行時に再検討が必要です。
> - SQLiteは単一Writer運用を前提とし、大量の同時書き込みには対応していません。
> - 既存データ入りの複雑なAlembic batch migrationの安全性は未検証です。
> - 親子間のorganization_id一致はRepository層で保証しており、DBレイヤーの直接操作による不整合は完全には防止されません。
> - PostgreSQL移行時には、複合外部キーやRLS（Row Level Security）等の導入を再検討する必要があります。
> - SQLiteでは `with_for_update()` が実質的な行ロックとして機能しません。コード上はDB方言によって処理を分け、SQLiteでは明示的トランザクション＋単一Writer方針を採用します。

## 2. モデル配置とEmbeddingProvider
- `EMBEDDING_MODEL_ROOT` 環境変数でモデル配置ルートを指定し、初期値は `data/models/` とします。
- 制限事項:
  - `.gitignore` の対象とする。
  - プログラムからの自動ダウンロードを一切禁止し、事前に配置されていることを前提とする。
  - ディレクトリトラバーサル防止（許可ディレクトリ外の参照禁止、シンボリックリンク等による外部参照防止）。
  - ローカルパスを利用者に返さない。
- 実モデルが未配置の場合:
  - 開発・デモ環境において環境変数 `ALLOW_MOCK_EMBEDDING=true` が設定されている場合のみ `MockEmbeddingProvider` へ切り替えます。この際、「埋め込み方式：Mock / 実モデル検索ではありません / 検索基盤の動作確認専用です」という警告を出力します。
  - 本番・顧客環境（上記変数が未設定）の場合はMockへ切り替えず、「ローカル埋め込みモデルが配置されていないため、検索を実行できません。」という日本語エラーを出力して停止します。
- **E5モデルのプロンプト制約**: `query: ` および `passage: ` 接頭辞の自動付与を実装し、自動テストで検証します。

## 3. SQLite FTS5とKeywordSearchProvider
- 起動時に環境のSQLiteを検査し、FTS5および `trigram` tokenizer 仮想テーブルの作成可否、日本語検索の動作を確認します。
- 共通インターフェース `KeywordSearchProvider` を作成し、検査結果に応じて以下の実装を切り替えます：
  1. `Fts5TrigramSearchProvider`
  2. `LikeSearchProvider` (フォールバック用)
  3. `MockKeywordSearchProvider` (テスト用)
- 3文字未満の検索語入力時は、trigramから自動的にLIKE（または完全一致）検索に切り替えるハイブリッド判定を採用します。

## 4. FAISSインデックス構成と更新の安全性
- 構成: `IndexFlatIP + IndexIDMap2` を採用し、L2正規化を行うことでコサイン類似度相当とします。
- インデックスは `organization_id` ごとに物理ファイルを分割します。
- FAISS内には「チャンクの数値ID」と「ベクトル」のみを保存し、原文やメタデータはDBから取得します。
- **インデックス更新の安全性**:
  1. 一時ファイルへインデックス生成
  2. 読み込み確認とチェックサム計算
  3. DB側のマッピング件数との照合
  4. 正常時のみアトミックにファイルを置換（失敗時は旧インデックスを保持）
  - DB側に `index_checksum` や `build_status` を管理する仕組みを用意します。

## 5. 検索フィルタの二重検証
セキュリティと権限管理のため、以下の二重検証を必須とします。
1. **検索候補生成前**: DBから対象組織、権限状態（`permission_confirmed`、有効期限、active、is_current 等）に合致する「有効なチャンクID群」を抽出し、ベクトル/キーワード検索時のフィルタ（IDリスト）として適用。
2. **結果返却直前**: 検索でヒットしたIDからDBレコードを再取得する際、全く同じアクセス権限条件を再適用して検証。FAISS等の出力を無条件に信用しません。

## 6. RRF統合と検索結果フォーマット
- キーワード検索順位とベクトル検索順位を `RRF (k=60)` で統合（k=20, 100等でも比較評価可能とする）。
- 検索結果の出力項目: 順位、チャンクID、ソースID、各スコア、出典タイトル、著者、ページ・時間範囲等。
- 原文全体は返却せず、スニペットの最大文字数制限を設けます。
- 出典情報はDBから取得したもののみを使用し、生成・推測は行いません。

## 7. 外部通信の遮断とテスト
- アプリケーションから外部通信を行わない設計とし、実行中にHugging Face Hub、外部AI API、モデル自動取得等への接続試行がないことを検証します（OSレベルでの物理遮断は行わず、コードと設定による防止策のテストを実施します）。
- `local_files_only=True` 等の制約をコードに適用し、オフライン環境として機能することを検証・明記します。

## 8. 品質評価と対馬向け確認スクリプト (CLI)
- 架空の「資料作成ルール」を用いた検索評価セットを作成し、LIKE / FTS5 / Vector / RRF の各方式で Recall@K (1, 3, 5)、MRR、権限違反混入件数等を計測します。
- 非技術者向けにCLIスクリプト `scripts/demo_search.py` を用意し、指定された検索文に対するハイブリッド検索結果（スコア、出典、除外件数等）をターミナルでわかりやすく確認可能とします。

## 9. Verification Plan (確認計画)
1. FTS5/trigramの利用可否検査とフォールバックが機能することの単体テスト。
2. `EMBEDDING_MODEL_ROOT` 制限および接頭辞付与ロジックの単体テスト。
3. 権限・期限切れ・他組織データがFAISSや検索結果に混入しないことの異常系テスト（二重検証の動作確認）。
4. FAISSインデックスの安全な更新（一時ファイル作成・チェックサム検証・ロールバック）の単体テスト。
5. 架空データを用いた Recall/MRR 評価スクリプトの実行と結果の報告。
6. CLI `demo_search.py` の実行結果の報告。
